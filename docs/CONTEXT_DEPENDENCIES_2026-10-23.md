# 작은 예산과 다른 파일의 보조 구현 보존

2026-10-23 · ContextOS 2.1.0, 빌드 2118.

## 결과

파일의 전체 크기로 먼저 제외하던 계획을 실제 전달할 코드 크기로 바꿨다. 요청한 구현과 참조한 보조 함수·상수·속성을 먼저 묶고, 작은 예산에서는 무관한 시그니처·채움 주석을 줄인다. 다른 파일의 구현도 이름과 import 경로를 확인해 함께 선택한다.

실제 MCP의 **200~250 추정 토큰**에서 여섯 개의 고정된 연쇄 의존 시나리오를 실행했다. 필요한 모든 본문이 남은 경우는 이미 최적화한 빌드 2117의 **0/6에서 6/6**으로 개선됐다. 여섯 경우 모두 예산을 지켰고, 무관한 구현 본문이 포함되지 않았다. 이 결과는 정해진 입력의 정보 보존 검사이며 일반적인 코드 수정 성공률을 뜻하지 않는다.

필수 구현 자체가 예산보다 크면 완전한 전달을 보장할 수 없다. 이때는 요청한 함수의 완전한 본문을 우선 남기고, 큰 타입은 명시적 부분 코드로 표시하며, 필수 코드 미포함·관련 위치·확인한 필요 토큰 수를 알린다. 같은 파일의 큰 보조 함수도 조용히 감추지 않는다. 필수 미포함이 감지된 전달은 절감 실적에 기록하지 않는다.

## 선택·전달 동작

- 이름을 명시한 구현 파일을 우선한다. 여러 파일·구현을 명시하면 모두 같은 필수 그룹으로 처리한다.
- `get_relevant_context`와 `read_optimized`가 같은 조립 경로를 사용한다. 계획의 포함 경로와 비용이 실제 슬라이싱 결과를 반영한다. 최적화된 본문 호출에서 계획을 다시 조립하는 중복 경로는 없다.
- 필수 그룹을 먼저 완성하고, 이후의 어휘상 관련 후보를 남은 예산에 넣는다. import 연결이나 최근 수정만으로 연결된 무관한 후보는 필수 구현을 찾은 후 본문 채우기로 사용하지 않는다.
- 일반 형식이 안 맞으면 파싱 결과를 재사용해 압축 형식으로 다시 계산한다. 이 단계는 선택한 함수 본문을 중간에서 자르지 않고 선택하지 않은 시그니처와 빈 줄·주석을 줄인다. 문자열 내용은 보존한다.
- 압축 후에도 필수 그룹이 크면 요청 본문·완전한 코드 단위부터 전달하고 미포함을 표시한다. 한 타입의 모든 구현이 안 들어가면 부분 코드 표기를 붙인다. 이 경우 파일 섹션이 있다는 것과 필요한 구현이 모두 있다는 것을 구분한다.
- 이미 전달한 호출자라도 보조 파일이 바뀌면 해당 구현을 다시 보낸다. 파일당 요청 심볼을 합쳐 같은 파일을 중복 섹션으로 보내지 않으며, 최종 전달한 본문만 세션 기억에 기록한다.
- 코드와 무관한 확인성 응답은 실제 어휘 신호를 확인한 뒤에만 훅의 본문 조립을 수행한다.

## 다른 파일을 찾는 범위

선택과 실제 전달이 공통 경로 해석을 사용한다. 상대 import는 호출 파일의 디렉터리에서 해석하고, 인덱스에 있는 허용 파일만 대상으로 한다. 상대 경로를 찾지 못했다고 다른 디렉터리의 같은 이름 파일로 대체하지 않는다.

이번에 실행 검증한 경로는 다음과 같다.

| 실제 MCP 검사 | 필요한 구현 | 예산 | 기존 | 개선 |
|---|---|---:|---:|---:|
| TypeScript named alias → 보조 함수 → 정규화 함수 | 세 파일의 호출자·검증·정규화 본문 | 250 | 누락 | 모두 보존 |
| TypeScript namespace import, `.js`가 가리키는 `.ts` | 호출자·접근 검사 본문 | 200 | 누락 | 모두 보존 |
| Python 상대 import·별칭·상수 | 호출자·검증 함수·키 초기화 | 250 | 누락 | 모두 보존 |
| Swift 같은 모듈의 자유 함수·`Type.method` | 호출자·검증 함수·규칙 메서드 | 250 | 누락 | 모두 보존 |
| re-export 별칭과 파일 간 순환 참조 | 호출자·재노출 경로·보조 구현 | 250 | 누락 | 모두 보존 |
| default와 named import 동시 사용 | 기본 함수와 별도로 사용하는 상수 | 250 | 누락 | 모두 보존 |

자동 테스트에서는 Swift의 단순한 타입 주석·생성자 바인딩과 `self.property`를 통한 메서드도 확인했다. 필요한 초기화와 해당 타입의 메서드를 보존한다. SDK 타입에 대한 프로젝트 확장이 있다는 이유로 SDK의 모든 멤버가 그 파일에 있다고 간주하지 않는다. Swift Package의 `Sources/<target>` 구분은 Package.swift가 있는 경우에 적용하고 명시한 import 대상도 고려한다.

동명 후보가 여러 개여서 자유 함수를 확정할 수 없거나, 로컬 경로·알려진 경로 별칭을 확인하지 못하거나, 문법 경계·읽기 한도를 확정할 수 없으면 미완료 상태를 드러낸다. 무시 파일·민감 경로·심볼릭 링크·루트 경계는 기존 파일 접근 계층을 계속 통과한다.

## 기존 질문에서의 검색·전달

최초 진단과 같은 `bf42f28` git archive, 같은 12개 질문·핵심 파일·예산을 사용했다. 각 바이너리는 자기 파서로 강제 재인덱싱했다. 작은 예산의 새 실패 사례를 숨기기 위해 기존 질문이나 답 파일을 바꾸지 않았다.

| 측정 | 기존 4,000 | 개선 4,000 | 기존 8,000 | 개선 8,000 |
|---|---:|---:|---:|---:|
| 계획 첫 파일이 핵심 파일 | 7/12 | 12/12 | 10/12 | 12/12 |
| 핵심 파일 섹션 포함, 명시적 부분 코드도 포함 | 9/12 | 12/12 | 12/12 | 12/12 |
| 필수 의존 코드의 미포함·확인 필요 경고 | 미검출 기능 | 7/12 | 미검출 기능 | 5/12 |
| 질문 응답의 로컬 추정 예산 준수 | 12/12 | 12/12 | 12/12 | 12/12 |

**파일 섹션 12/12는 필수 코드 전체 전달 12/12를 뜻하지 않는다.** 이 프로젝트의 넓은 질문은 실제 보조 구현을 따라가면 기존 예산을 넘기도 한다. 개선 버전은 이를 경고하고, 큰 파일 때문에 요청 파일 자체가 통째로 빠지는 일을 줄인다. 기존 버전의 경고 0건은 의존 구현이 모두 들어갔다는 증거가 아니다.

이전 250 토큰 단일 파일 검사 네 개는 전후 모두 4/4다. 이번 여섯 개 검사는 별도의 다른 파일 정보 보존 검사다. 실제 모델 토크나이저·답변 정확도·배터리 소모량을 측정한 결과는 아니다.

## 성능과 자원 사용

비교 기준은 직전 빌드 2117의 최적화된 작업 소스다. 같은 Mac의 Release 바이너리, Swift 파일 500개·함수 12,000개·소스 1,985,720bytes를 사용하고, 버전마다 별도 프로세스를 7회씩 교차 실행했다. 표는 각 프로세스의 반복 중앙값을 다시 중앙값으로 비교한 값이다. OS·다른 앱 부하는 고정하지 않았으며 모든 최종 실행을 포함했다.

| 측정 | 이미 최적화된 기존 버전 | 이번 개선 |
|---|---:|---:|
| 최초 인덱싱 | 279.667ms | 278.598ms |
| 변경 없는 인덱스 확인 | 16.758ms | 16.121ms |
| 검색 순위 계산 | 38.762ms | 38.933ms |
| 인덱스 확인·검색·본문 조립 전체 | 279.452ms | 86.482ms |
| 최대 RSS 중앙값 | 24.578MiB | 25.469MiB |

전체 처리는 약 **69.1% 빨라졌고**, 최초 인덱싱과 순위 계산은 비슷했다. 메모리는 약 **0.89MiB 증가**했다. 이 합성 검사에서 메모리가 줄었다고 주장하지 않는다. 성능용 입력의 경로·점수·추정 토큰·본문을 합친 해시는 14회 모두 `3e9c09c35c92b5a62b460bb4b2cfca7236fec8b719704cf98007434369555922`로 동일했다.

속도와 메모리를 지키기 위해 다음을 적용했다.

- 선택한 코드에 실제 등장한 이름만 SQLite 인덱스에서 찾는다. 프로젝트의 전체 심볼 지도를 전달 단계에서 다시 만들지 않는다.
- 파일은 준비한 어휘 스캔·선언 범위를 재사용한다. 압축 재시도·여러 심볼 요청에 매번 파일을 다시 읽고 파싱하지 않는다. 소유 타입 탐색도 타입 목록만 대상으로 한다.
- JavaScript/Python의 import 경로 지도는 필요할 때만 생성한다. Swift 초기화 선언 검사는 UTF-8의 짧은 확인 뒤에만 정규식을 적용한다.
- 한 번의 전달에서 소스 읽기는 총 4MiB, 조립 파일은 32개로 제한한다. 순환은 파일별 요청 심볼 집합을 합쳐 종료한다. 한도에 걸린 필수 구현은 미포함 상태를 표시한다.
- 낮은 우선순위 후보가 연속 8회 안 들어가면 추가 본문 탐색을 멈추고 남은 후보를 목차로 안내한다. 이 제한은 필수 의존성 탐색을 무관한 후보 채우기로 바꾸는 규칙이 아니다.
- 기존 30초/저전력 60초 집계, 잠금·잠자기 중 중단, 갱신 합치기, 활동 로그 읽기 제한과 세션 기억 상한을 유지했다. 관련 다섯 소스 파일은 이전 스냅샷과 SHA-256이 같다.

## 검증·적용

- macOS 자동 테스트 **428개 통과**, Windows 전용 3개 건너뜀. 이식용 준비 프로필 **15개 통과**, 해당 환경의 미지원 경로 5개 건너뜀.
- 새 자동 검사 14개: 연쇄 참조·별칭·namespace·상수·re-export·순환·Swift 초기화/소유 타입/모듈·보조 파일 변경·부족한 예산·무시 파일 경계·여러 명시 파일·짧은 호출 파일의 무관 참조 등을 확인했다.
- 실제 MCP의 새 여섯 시나리오와 기존 1·30·100·250·500 예산, fresh·중복 전달·강제 인덱싱·민감 파일·링크·프로젝트 경계·잘못된 요청 복구 검사를 통과했다.
- 파서 개정 정보로 기존 인덱스도 한 번 갱신한 뒤 평상시 증분 경로를 사용한다. 도구 이름·입력 계약은 유지한다.
- 기존 서명 팀·App Group·위젯을 유지한 빌드 2118을 `<local-app-bundle>`에 설치했다. 호스트·CLI·MCP·위젯의 네 실행 파일 해시가 검증 패키지와 같고 서명·doctor 검사도 통과했다. 패키지의 실제 MCP에서도 여섯 의존 시나리오를 다시 통과했다.
- 실제 대시보드·AI 사용량·개발 시간 화면을 확인했다. 개인 정보 숨기기·기존 VS Code 활동 설정·누적 기록을 유지했다. 기존 일부 집계 불가와 당일 개발 활동 미관측 상태도 표시한다.
- 직전 빌드 2117은 `<local-backup-app>`에 보존했다. 이미 실행 중인 Codex·Claude의 MCP에는 이전 코드가 남을 수 있으므로 AI 도구를 재시작하면 새 바이너리를 사용한다.
- 소스·테스트·검사 도구의 2117→2118 차이는 `upgrade-from-2117.patch`로 보존하고 실제 작업 파일을 바꾸지 않는 역적용 검사로 확인했다.
- 검증 후 이번 작업의 빌드·캐시·임시 사본 13,746개, 논리 크기 약 1.37GB를 정리했다. 설치 앱·검증 패키지·복구 앱·소스·검사·증거·실제 인덱스·설정·사용 기록은 유지했다. 창을 닫은 뒤 새 앱이 메뉴바에서 계속 실행되는 것도 확인했다. 삭제 범위는 로컬 전용 `cleanup.json`에 보관한다.

합성 입력의 질문별 결과·성능 측정·소스 해시는 [공개 검증 자료](benchmarks/context-dependencies-20261023/), 요약은 [summary.json](benchmarks/context-dependencies-20261023/summary.json)에 있다. 새 실제 MCP 검사 도구는 `scripts/audit_dependency_context.py`다. 실행 로그·설치·정리 원자료는 로컬 전용이며 저장소에서 제외한다. 공개 범위는 [검증 자료 안내](benchmarks/README.md)를 따른다.

## 남는 경계

언어 전체의 AST·타입 검사기는 아니다. 동적 호출·다형성·복잡한 별칭·매크로·모든 import 문법과 프로젝트별 경로 설정을 완전히 해결하지 않는다. 외부 패키지·무시 경로를 임의로 읽지 않는다. 미포함 표시가 없다는 것만으로 정적 분석이 모든 런타임 의존성을 증명한 것은 아니다.

필수 코드가 실제 예산보다 크면 더 큰 예산이나 더 구체적인 함수 단위 요청이 필요하다. 코드 줄을 임의로 잘라 이 한계를 숨기거나, 전달하지 않은 본문을 절감 실적으로 계산하지 않는다.
