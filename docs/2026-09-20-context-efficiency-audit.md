# ContextOS 동작·효율 점검 — 2026-09-20

이번 수정의 기준은 로컬에서 쓰는 ContextOS의 핵심 약속이다. 필요한 코드를 찾아서 보존하고, 전달량을 줄이며, 절감량을 과장하지 않아야 한다. 새 서버, 외부 API, 추가 패키지 없이 기존 Swift/SQLite 구조에서 고쳤다.

## 결론

기존 테스트 189개는 통과했지만 실제 사용 경계 조건에 결함이 있었다. 먼저 추가한 재현 테스트 10개 중 9개가 기존 코드에서 실패했다. 이후 발견한 함수 본문 누락도 별도로 재현했다. 최종적으로 회귀 테스트 17개를 추가했고, 전체 206개 테스트가 통과했다.

토큰 절감은 실제 stdio MCP 프로세스와 이 저장소에서 확인했다. 다만 아래 토큰 수는 **로컬 문자 기반 추정치**이며 모델의 실제 과금 토큰이나 전체 대화 비용 절감률은 아니다. 작업 완료 정확도를 측정한 LLM 벤치마크도 아니다.

## 확인한 원인과 수정

| 문제 | 원인·영향 | 수정과 검증 |
|---|---|---|
| 파일을 지정해도 엉뚱한 파일 선택 | `Package.swift`를 `package`, `swift`로 쪼개 테스트 심볼과 모든 Swift 경로를 매칭했다. | 파일명·상대 경로·프로젝트 안의 절대 경로를 별도로 처리한다. 명시한 파일을 우선하고 무관한 Git 변경 가산점은 적용하지 않는다. 동명 파일 구분도 검사했다. |
| 문서 이름의 잘못된 오타 보정 | 어휘에 심볼만 들어가 `README`를 `read`로 바꿨다. 동률 후보는 Set 순회 순서에 영향을 받았다. | 파일 경로도 어휘에 포함하고, 동률이면 원래 단어를 유지한다. `MCPServer`, `HTTPClient`의 약어 경계도 분리한다. `SessionMemory.isUnchanged` 같은 심볼 표기는 계속 검색된다. |
| 큰 파일의 필요한 함수 누락 | 전체 파일 크기로 먼저 제외한 뒤, 선택된 파일만 잘랐다. 작은 함수가 예산에 충분히 들어가도 시도하지 않았다. | 관련도 순서대로 실제 슬라이스를 만든 후 예산을 적용한다. 600줄짜리 무관한 함수 옆의 필요한 본문이 250토큰 예산에서 보존되는지 검사했다. |
| 토큰 예산 초과 | 선택된 파일 크기만 세고 목차·파일 제목·MCP 헤더를 뒤에 붙였다. | 제목·중복 표시·목차를 포함한 최종 텍스트를 계산한다. 목차는 남은 예산만 사용한다. MCP에서 별도 헤더를 다시 붙이지 않는다. |
| 절감량 계산 단위 불일치 | 원본은 UTF-8 바이트 수/코드 밀도, 응답은 문자 수/일반 텍스트 밀도로 계산했다. 한글이 많을수록 왜곡됐다. 목차 비용도 빠졌다. | 원본 대안과 최종 응답에 같은 문자 단위와 추정기를 쓴다. 통째로 보낸 한글 파일이 절약으로 잡히지 않도록 검사했다. 모델별 정확도 근거가 없는 ±5–8% 문구도 제거했다. |
| 중복 제거가 오히려 더 큼 | 짧은 본문에도 긴 한국어 안내와 추가 헤더를 붙였다. | 중복 표시를 줄이고, 실제 본문보다 짧을 때만 쓴다. 예산 때문에 보내지 못한 본문은 전달 완료로 기록하지 않는다. 수정·TTL·`fresh=true` 검증은 유지했다. |
| 필요한 함수의 뒷부분이 잘림 | 문자열·주석의 `}`를 코드 블록 종료로 셌다. `return`이 통째로 빠지는 사례가 재현됐다. | 따옴표·이스케이프·주석을 구분한다. Rust lifetime을 문자열로 오해하지 않는다. 중첩 문자열 보간처럼 경계가 불확실한 경우에는 더 많은 내용을 보존한다. |
| 강제 재인덱싱이 강제 동작하지 않음 | `forceReindex`를 전달하지 않았고 `reindex`도 일반 증분 경로를 호출했다. 크기·mtime이 같으면 변경이 계속 안 보였다. | 강제 경로에서는 메타데이터와 해시 빠른 경로를 모두 건너뛰고 재파싱한다. 파일 감시는 기존처럼 증분 인덱싱을 유지한다. |
| MCP와 훅이 동시에 인덱싱할 때 경쟁 | 쓰기 잠금 전에 기존 파일 목록을 읽었다. 서로 낡은 목록을 기준으로 같은 경로를 삽입할 수 있었다. | `BEGIN IMMEDIATE`로 잠근 뒤 목록을 읽는다. 실패 시 rollback하고, WAL 설정 전 busy timeout을 적용한다. 8개 동시 인덱서가 41개 파일·심볼을 보존하는지 검사했다. |
| 프로젝트 경계·잘못된 경로 | 파일 심볼릭 링크를 따라 프로젝트 밖 본문을 읽었다. 없는 루트도 `.contextos` 생성으로 실제 디렉터리가 될 수 있었다. | 스캔에서 심볼릭 링크와 일반 파일이 아닌 항목을 제외한다. 전달 직전에도 실제 경로가 루트 안인지 확인한다. 없는 루트는 생성하지 않고 실패한다. |

슬라이스 선택 변경으로 불필요한 작업이 늘지 않도록, 최소 파일 제목조차 남은 예산에 들어가지 않으면 본문 읽기·파싱을 건너뛴다. 절감량 계산을 위해 전체 원본 파일들을 하나의 큰 문자열로 보관하지도 않는다. 슬라이스 안내를 합친 결과가 원본보다 크면 원본을 보낸다.

## 실제 MCP 비교

수정 전 `8b0301d`에서 빌드한 실행 파일을 보관해 동일한 임시 프로젝트를 입력했다. MCP 초기화부터 도구 호출·응답까지 실제 프로세스로 실행했다. 벤치마크는 macOS sandbox에서 사용자 분석 DB 쓰기를 막아 대시보드 누적 절감량을 오염시키지 않는다.

| 입력·측정 | 수정 전 | 수정 후 |
|---|---:|---:|
| `Package.swift` 요청, 3파일 fixture | 테스트 파일이 1순위, 3파일 선택 | 요청 파일 1개 선택 |
| 큰 파일의 `target`, 예산 250 | 관련 함수 본문 없음 | 필요한 본문 포함, 약 31토큰 |
| 위 파일 원문 크기 | 약 4,665토큰 | 함수·목차를 포함한 응답 약 31토큰 |
| 같은 질문 첫 응답 → 반복 응답 | 약 46 → 48토큰 | 약 31 → 12토큰 |
| 전체 응답, 예산 100 | 약 165토큰 | 약 99토큰 |
| 전체 응답, 예산 250 | 약 293토큰 | 약 247토큰 |
| 전체 응답, 예산 500 | 약 520토큰 | 약 485토큰 |
| 변경 없는 10파일 강제 재인덱싱 | 재파싱 심볼 0개 | 재파싱 심볼 10개 |

이 큰 파일 fixture에서는 원문 대비 응답 크기가 약 99.3% 작다. 무관한 본문이 길도록 만든 사례이므로 일반 프로젝트의 평균 절감률로 해석하면 안 된다. 수정 후 반복 호출은 같은 fixture의 첫 응답보다 약 61.3% 작다.

아주 작은 예산에서는 전달할 본문이나 목차가 없을 수 있다. 예산 1에서는 빈 코드 응답, 예산 30에서는 약 29토큰의 목차가 반환됐다. 예산을 몰래 넘겨 본문을 채우지 않는다.

실제 ContextOS 저장소에서도 확인했다. 두 실행 파일 모두 동일한 수정 중 작업 트리를 읽었다.

| 실제 저장소 요청 | 수정 전 | 수정 후 |
|---|---|---|
| `ContextOptimizer.swift`, 예산 8,000 | 관련 없는 파일을 포함해 7개 선택 | 지정 파일 1개 선택 |
| `bodyHash`, 예산 1,200 | 약 1,556토큰인데 `func bodyHash` 정의 없음 | 약 1,200토큰, 정의 포함 |

**실행 속도가 빨라졌다고 주장하지는 않는다.** 작은 fixture의 10회 warm 조회 중앙값은 Debug 기준 약 77.57→76.95ms로 비슷했다. 실제 저장소 `bodyHash` 단일 호출은 약 270.63→372.49ms였다. 이제 큰 파일의 본문을 읽고 필요한 함수를 보존하는 비용이 포함되며, 단일 측정과 시스템 부하는 분리하지 않았다. 확인된 개선은 검색 범위·본문 보존·전달량·예산 준수다.

## 다음 보완의 우선순위와 범위

1. **실제로 사용하는 질의·문법 fixture를 축적한다.** 이번 17개 회귀 테스트와 MCP 벤치마크가 출발점이다. 새 Swift/JS/Python 코드 형태에서 검색 실패나 본문 누락이 생기면 그 사례를 먼저 추가한다. 테스트 개수 자체를 품질 점수로 쓰지 않는다.
2. **파서의 정밀도를 사용 사례에 맞춰 보완한다.** 여전히 정규식·줄 단위 휴리스틱이며 완전한 AST 파서는 아니다. 복잡한 정규식 리터럴, 여러 줄 선언, 언어별 새 문법 전체를 보장하지 않는다. 모든 언어를 한 번에 교체하기보다 실제 사용하는 문법부터 정확성과 비용을 비교하는 편이 이 프로젝트에 맞다.
3. **속도가 문제일 때만 큰 프로젝트로 프로파일링한다.** 증분 인덱싱도 디렉터리 메타데이터 스캔은 한다. 현재 결과만으로 벡터 DB·외부 모델·상주 서버·분산 인덱싱을 추가할 이유는 없다. 우선 파일 수별 스캔·Git 조회·파싱 시간을 나눠 측정해야 한다.
4. **표시 수치의 의미를 유지한다.** 로컬 추정 절감량과 실제 에이전트 사용량은 다르다. 과거 누적 절감 기록은 새 계산법으로 소급 보정하지 않았다. 전체 작업 비용 절감은 에이전트의 도구 선택·재조회·대화 길이까지 포함한 별도 비교가 필요하다.

수정은 작업 트리와 새 빌드에 반영했다. 이미 실행 중인 MCP 프로세스나 설치된 앱 번들은 자동으로 교체하지 않았다. 설치본 반영에는 프로젝트의 기존 빌드·설치 절차와 에이전트/MCP 재시작이 필요하다.
