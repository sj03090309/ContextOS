# ContextOS 요약 품질·상시 실행 비용 점검

점검일: 2026-10-22 (한국 시간). 기준 소스: `bf42f28`. 목적은 한 사용자의 Mac에서 하루 종일 켜 두는 로컬 개발 보조 도구의 정확성과 자원 사용을 점검하는 것이다. 대규모 조직의 운영 체계나 모든 언어의 완전한 지원을 출시 조건으로 추가하지 않았다.

이 문서는 빌드 2116 시점의 최초 진단이다. 이후 요청한 검색·슬라이싱 개선 결과와 빌드 2117 검증은 [요약 품질 개선 보고서](CONTEXT_QUALITY_2026-10-22.md)에 별도로 기록했다.

## 판단

ContextOS의 핵심 기능은 **AI 문장 요약이 아니라 관련 소스 선택·함수 슬라이싱·전달 중복 제거**다. 비용 없이 로컬에서 작동하고, 작은 예산·민감 파일 경계·중복 전달 제거는 실제 실행 검사에서 작동한다. 반면 관련 파일을 빠짐없이 찾거나 변경에 필요한 모든 구현을 보존하는 기능으로 신뢰하기에는 빈틈이 있다. 현재는 파일을 찾는 보조 수단으로 유용하며, 선택된 내용만으로 수정의 타당성을 확정하는 용도로 쓰면 누락 위험이 있다.

이번 변경은 검색 순위를 바꾸지 않고 실행 비용을 낮췄다. 품질 문제를 숨기기 위해 검색 결과나 성공 기준을 사후 변경하지 않았다. 훅의 `정확도`라는 표현은 실제 의미에 맞게 `선택 점수`로 고쳤다.

## 1. 요약이 실제로 얼마나 작동하는가

### 방법

- 수정 전 커밋의 `git archive` 사본을 고정했다. `.git`이 없는 사본이므로 최근 편집·커밋에 따른 가산점은 적용되지 않는다.
- 구현을 찾는 12개 질문과 각 질문에서 필요한 핵심 파일 하나를 미리 지정했다. 영어 식별자·한국어·복합 질문·명시적 파일명을 섞었다.
- 실제 stdio MCP 바이너리의 `get_relevant_context`와 `read_optimized(fresh=true)`를 모두 실행했다. 기본 예산 8,000과 더 작은 4,000 추정 토큰을 각각 확인했다.
- 별도 합성 프로젝트 4개에서는 요청한 함수 본문뿐 아니라 보조 함수·화살표 함수·큰 타입의 필수 정보가 남는지 확인했다.
- 계정 설정·실제 대화 기록·기존 분석 DB·네트워크를 차단한 임시 홈을 사용했다. 모델에 답을 생성시키거나 작업 성공률·청구액 절감을 측정한 실험은 아니다.

### 결과

| 고정된 12개 질문 | 4,000 추정 토큰 | 기본 8,000 추정 토큰 |
|---|---:|---:|
| 핵심 파일이 계획의 첫 번째에 등장 | 4/12 | 5/12 |
| 핵심 파일이 계획의 상위 3개에 등장 | 5/12 | 6/12 |
| 실제 본문 응답에 핵심 파일이 포함 | 5/12 | 8/12 |
| 응답이 로컬 추정 예산을 준수 | 12/12 | 12/12 |

이 수치를 제품 전체의 정확도 백분율로 일반화할 수는 없다. 이 저장소의 특정 질문 세트와 예산에 대한 진단 결과다. 함수 본문이 있다는 것 역시 답변이나 수정이 맞다는 뜻은 아니다.

합성 정보 보존 실험은 250 추정 토큰에서 다음과 같았다.

| 질문/소스 | 필요한 정보 | 결과 |
|---|---|---|
| Python `target` 함수와 큰 무관 함수 | 요청 함수의 반환 본문 | 보존 |
| `login`이 같은 파일의 `verify_signature` 호출 | 보조 함수의 검증 구현 | 누락; 시그니처만 남음 |
| TypeScript `export const authorize = (...) => ...` | 접근 검사 본문 | 함수로 인식하지 못함 |
| 큰 Swift `AccountService` 타입 | 계정 처리 본문 | 타입 전체가 선택되어 작은 예산에 맞지 않음 |

기존 MCP 회귀 시나리오에서는 약 4,665 추정 토큰의 Python 원문에서 필요한 본문을 31 추정 토큰으로 전달했다. 반복 요청은 12 추정 토큰으로 줄었고, `fresh=true`는 본문을 다시 전달했다. 1·30·100·250·500 토큰 예산, 강제 재인덱싱, 민감 파일·중첩 ignore·규칙 링크·보호 루트 처리도 통과했다. 이러한 기능 검사는 위의 검색·정보 누락 문제와 함께 판단해야 한다.

두 예산의 24개 질문 모두 수정 전후의 **선택 경로와 전달 본문 SHA-256이 같았다**. 합성 보존 실험의 성공·실패도 같았다. 성능 변경으로 품질이 개선됐다는 주장을 하지 않는다.

## 2. 부족한 점과 개선 순서

### 우선 1: 관련 구현을 보존하는 선택·슬라이싱

현재 `CodeSlicer`는 질의 단어가 맞는 심볼의 본문과 나머지 시그니처를 남긴다. 호출한 보조 함수의 구현, 전역 상수, 속성 초기화와 같은 필요한 의존 정보는 보존하지 못할 수 있다. 타입 이름이 맞으면 타입 전체를 남겨 예산을 소진하는 반대 문제도 있다.

개선안은 우선 Swift·Python·TypeScript의 실제 사용 문법에서 **선택한 함수 + 같은 파일의 직접 보조 함수 + 사용한 상수/속성**을 제한적으로 묶는 것이다. 예산이 부족하면 본문이 빠진 이유와 추가로 필요한 파일·심볼을 명시해야 한다. 처음부터 모든 언어의 완전한 AST를 구현할 필요는 없다. 정확하게 지원할 수 없는 문법에서는 원문 또는 명시적 불확실성으로 돌아가야 한다. 완료 기준은 위 누락 실험의 필수 정보 보존과 작은 예산 준수다.

### 우선 2: 질문을 더 정확하게 해석하고 테스트 편향 줄이기

질문은 파일명·경로·심볼·import의 단어로 바뀐다. 긴 테스트 함수 이름이 많은 질의 단어를 포함하면 실제 구현보다 높은 점수를 얻는다. 반대로 한국어 사전에 없는 `컨텍스트`·`요약` 같은 표현, 다른 형태의 영어 단어, 문맥으로만 표현한 요구는 놓칠 수 있다. 실제로 구현 이름을 포함한 복합 질문에서도 테스트나 작은 주변 파일이 먼저 나왔다.

개선안은 전체 식별자 일치를 단어 분해 일치와 구분하고, 테스트를 요청하지 않은 구현 탐색에서 테스트의 우선순위를 조정하는 것이다. 한국어 사전은 실제 실패 질문을 바탕으로 확장하되 일반 단어를 무조건 여러 동의어로 늘려 잡음을 키우지 않아야 한다. 위 고정 질문과 다른 저장소의 독립 질문을 함께 유지해 자기 저장소에만 맞춘 규칙을 막는 것이 좋다.

### 우선 3: 계획과 본문 예산의 차이·점수의 의미

`get_relevant_context`는 전체 파일의 추정 크기로 먼저 파일을 제외한다. `read_optimized`는 전체 순위를 얻은 뒤 슬라이스가 들어가는지 확인한다. 그래서 계획에서는 빠진 큰 파일이 본문에서는 들어가기도 하고, 핵심 타입을 통째로 남기면 본문에서도 빠진다. 파일 목록의 `Read ONLY` 문구는 이 휴리스틱 결과를 과도하게 확정적으로 보이게 한다.

`contextScore`는 점수 질량의 예산 포괄률과 최상위 일치 강도를 조합한 값이며, 검증된 정확도·작업 성공 확률이 아니다. 훅의 잘못된 `정확도` 표현은 이번에 수정했다. 다음 단계에서는 계획에도 예상 슬라이스 비용을 쓰거나 최소한 전체 파일 비용이라는 점을 표시하고, 점수는 `선택 점수`·`예산 포괄률`로 설명하는 것이 적절하다.

### 우선 4: 파서와 관계 그래프의 명시적 지원 범위

`HeuristicParser`는 정규식·줄·괄호/들여쓰기 추정 방식이다. TypeScript 화살표 함수가 빠지는 등 실제 언어의 모든 선언을 인식하지 못한다. import 그래프도 모듈의 마지막 이름을 파일명에 연결하는 방식이라 Swift의 타깃/모듈 관계나 별칭을 정확한 호출 관계처럼 해석할 수 없다.

자주 쓰는 선언·언어를 순서대로 보완하고 문법별 정보 보존 fixture를 추가하는 것이 먼저다. 그래프 연결은 참고 근거로 유지하되 관계가 없다는 이유로 필요한 파일을 배제하지 않아야 한다. 전체 파서 교체는 크기·실행 비용·실패 시 원문 보존을 비교한 뒤 결정하면 된다.

### 우선 5: 중복 집계 경로와 긴 기록의 비용

동시 세션용 `ConcurrentUsageReader`와 전체 이력용 `AgentSessionReader`가 같은 로그를 따로 탐색·해석한다. 두 경로의 집계 범위와 불완전 데이터 처리도 다르므로 숫자를 그대로 하나로 합치면 안 된다. 후속 개선은 메타데이터 파싱과 변경 감지만 공유하고, 각 화면의 집계 범위는 명시적으로 유지하는 것이다.

이번에 활동 상태 판정에는 읽기 예산을 적용했지만, 전체 이력 집계의 기존 `LineReader.forEachLine`은 아주 큰 한 줄에 비례하는 버퍼를 여전히 만들 수 있다. 모든 앱 메모리에 절대 상한을 만들었다는 뜻은 아니다. 후속 작업에서는 이 경로에도 제한 읽기와 `일부 누락` 상태를 함께 도입해야 한다. 숫자를 조용히 잘라서 메모리만 줄이면 집계의 신뢰성이 나빠진다.

쿼리마다 전체 파일 메타데이터를 다시 스캔하는 비용도 남아 있다. 파일 감시 세대와 검증 주기를 사용해 줄일 수 있지만, 여러 MCP 프로세스·훅과 외부 편집에서도 최신성이 유지돼야 한다. 현재의 최신성 불변식을 희생하며 시간만 캐시하는 방식은 피해야 한다.

## 3. 이번에 적용한 최적화·오류 수정

- ASCII 식별자는 UTF-8 바이트 경로로 분해하고, 한국어·악센트·이모지는 기존 Unicode 경로를 유지한다. 파일 참조 정규식과 언어 파서 정규식은 매번 컴파일하지 않고 재사용한다. 심볼의 완전 일치를 찾으면 같은 파일의 나머지 심볼 검색을 중단한다.
- 창이 닫힌 상태의 로그 집계 요청을 2초에서 30초 단위로 합친다. 저전력 모드 또는 높은 열 상태에서는 60초로 늘린다. 창을 열면 보류 요청을 취소하고 즉시 읽는다. 연속 로그가 들어와도 첫 예약 시각을 미루지 않는다.
- 활동 평가와 디렉터리 재탐색은 각각 한 번에 하나만 실행하고 후속 요청을 합친다. 화면 잠자기·잠금·사용자 세션 비활성 중에는 관련 갱신 타이머를 중단하고 복귀 시 다시 읽는다.
- 활동 판정은 최신 64개 로그를 대상으로 한 번에 최대 4MiB, 한 JSON 레코드 최대 256KiB를 읽는다. 남은 데이터는 후속 평가에서 이어 읽는다. 누락된 증거로 응답 완료를 만들어 내지 않고 `unknown`으로 처리하며 새 시작·종료 증거로 복구한다.
- MCP 전달 기억은 기본 2,048개로 제한하고 만료 항목을 제거한다. 오래된 항목이 밀려나면 본문을 다시 보내므로 필요한 코드를 숨기는 방식으로 메모리를 줄이지 않는다.
- 오래된 디렉터리의 수정 시각으로 하위 세션을 버리던 오류를 수정했다. 이 Mac에서는 `.codex/sessions/2026`의 수정 시각이 10월 1일인 반면 당일 로그 폴더는 10월 22일이었다. 파일 추가와 기존 파일 append는 상위 디렉터리의 수정 시각을 갱신하지 않는다. 하위 로그 메타데이터를 확인하고 본문 읽기만 제한하며 디렉터리 심볼릭 링크는 따라가지 않는다.
- 패키지의 실행 코드에서 개발용 디버그 메타데이터를 제거한 뒤 서명한다. 빌드 원본의 코드는 바꾸지 않는다. 위젯 타깃에 빠져 있던 `ModelUsageSummary.swift`도 등록해 기존 위젯을 포함한 패키지가 다시 빌드되게 했다.

### 검색 성능 비교

같은 Mac·Release 빌드, 합성 Swift 파일 500개·함수 12,000개·1,985,720 bytes, 8,000 추정 토큰 예산을 사용했다. 전후 각각 3회 실행하고 실행 순서를 교차했다. 표는 프로세스별 반복 측정 중앙값의 중앙값이다. 다른 앱을 종료하거나 CPU를 고정하지 않았다.

실제 고객 저장소의 시간·정확도, 모델의 실제 토큰 수, 청구액 절감을 보장하는 측정은 아니다.

### 숨겨진 앱의 상시 실행 비용

별도 임시 홈에서 실제 앱 실행 파일을 실행해 80개 합성 세션·각 300개 토큰 기록을 만들고, 한 로그에 매초 활동·토큰 이벤트를 추가했다. 두 프로세스 모두 합성 세션 80개를 실제로 읽었고 실행 중 추가분을 캐시에 반영했는지 확인했다. Mac 잠금 해제 후 각각 10초 준비·약 65초 계측한 한 쌍의 결과다. 번들 외 실행으로 위젯 공유는 제외했다. 다른 앱은 종료하지 않았다.

| 측정 | 변경 전 | 변경 후 |
|---|---:|---:|
| 평균 CPU, 코어 하나를 100%로 표시 | 0.176% | 0.062% |
| 계측 구간 CPU 시간 | 114.62ms | 40.80ms |
| 구간 중 관측한 최대 physical footprint | 25.31MiB | 23.84MiB |
| package idle wakeup 횟수 | 11 | 18 |
| interrupt wakeup 횟수 | 1,014 | 982 |
| 커널 집계 디스크 읽기 | 278,528 bytes | 823,296 bytes |
| 커널 집계 디스크 쓰기 | 4,096 bytes | 4,096 bytes |

이 짧은 입력에서 CPU 시간은 약 64.4% 감소했지만 절대 사용량 자체가 작고 wakeup·읽기량은 모두 개선되지 않았다. 디스크 캐시·OS 스케줄링과 실행 순서의 영향도 있다. 이 결과로 전력 소비나 배터리 지속 시간이 64% 개선됐다고 말할 수 없다. 실제 하루 사용·절전 복귀를 포함한 장시간 비교는 별도 관측이 필요하다.

## 4. 검증·실행 결과와 정리

테스트는 native SwiftPM에서 398개 통과·Windows 전용 3개 제외, portable 준비 프로필에서 15개 통과·해당 프로필 밖/Windows 전용 5개 제외다. Windows에서 실행했다고 주장하지 않는다. 연속 이벤트 합치기·취소, Unicode 경계, 전달 기억의 만료·상한, 큰 레코드와 여러 세션의 이어 읽기, 오래된 폴더 아래 재개한 세션, 디렉터리 순환 링크를 포함한다.

위젯은 arm64·x86_64 Release 빌드에 성공했다. 최종 패키지의 실제 CLI·MCP에서도 연결 설정 왕복·보호 경계·작은 예산 검사를 다시 통과했다. 기존 개발 서명과 App Group을 유지해 `<local-app-bundle>`에 **2.1.0 / 빌드 2116**을 설치했다. 앱·CLI·MCP·위젯의 SHA-256이 검증한 패키지와 모두 같다. 패키지 파일 총량은 15,772,909 → 13,713,741 bytes로 약 13.1% 줄었다.

실제 화면에서 대시보드의 `Codex 작업 중`과 진행 세션, AI 사용량 화면, 개발 시간 화면, 유지된 개인정보 숨김 설정을 확인했다. 화면을 닫은 뒤 실제 사용자 기록을 읽는 앱의 한 시점 physical footprint는 41.9M, 시작부터의 peak는 84.5M이었다. 이 값은 하루 넘게 실행된 이전 프로세스나 합성 입력과 같은 조건의 비교가 아니다.

기존 AI 도구에 이미 연결된 MCP 프로세스는 이전 실행 이미지를 유지한다. **Codex·Claude Code를 다음에 재시작하면 새 MCP 실행 파일을 사용한다.** 진행 중인 사용자 AI 세션을 강제 종료하지 않았다. 이전 앱은 `<local-backup-app>`에 복구용으로 남겼다.

재생성 가능한 Swift/Xcode 빌드 출력, Python 바이트코드, 이번 점검의 임시 소스·실행 파일·중복/실패 패키징 출력을 정리했다. 총 **16,027개 파일, 논리 크기 1,629,240,151 bytes(약 1.63GB)**다. `du`가 보고한 정리 대상의 할당량 합계는 1,674,309,632 bytes이며 APFS 공유 블록·압축을 고려한 실제 여유 공간 증가량과는 다를 수 있다. 소스·테스트·정식 자산·현재 인덱스·사용 기록·사용자 설정·기존 그래프·검증된 최종 패키지·복구용 앱은 보존했다. 빌드를 다시 실행하면 필요한 빌드 캐시는 재생성된다. 경로별 수치는 로컬 전용 `summary.json`에 보관한다.

합성 입력의 품질·성능 결과는 [공개 검증 자료](benchmarks/context-audit-20261022/)에 있다. 기기별 경로·설치·정리 정보를 포함한 `summary.json`은 로컬 전용으로 보관하며 저장소에서 제외한다. 공개 범위는 [검증 자료 안내](benchmarks/README.md)를 따른다.

재현:

```sh
swift test
swift build -c release
python3 scripts/benchmark_context.py --binary .build/release/contextos-mcp --verify
python3 scripts/audit_context_quality.py --binary .build/release/contextos-mcp --corpus /path/to/fixed-git-archive --budget 8000 --output /tmp/context-quality.json
.build/release/contextos-bench /tmp/nonexistent-unique-fixture 500
python3 scripts/benchmark_background.py --baseline /path/to/baseline/ContextOSApp --candidate /path/to/candidate/ContextOSApp --seconds 65 --output /tmp/background.json
```

`benchmark_background.py`는 두 시험 앱을 차례로 잠깐 실행한다. 임시 홈의 합성 로그 80개가 실제 집계됐는지와 실행 중 append가 캐시에 반영됐는지를 확인한 뒤 계측한다. 실제 계정 설정·대화 기록·위젯 공유 데이터는 읽거나 바꾸지 않는다.
