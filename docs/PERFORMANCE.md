# 검색 최적화 측정

쿼리 한 번에서 파일명·경로·심볼·import를 나눈 어휘를 재사용하도록 바꿨습니다. 이전에는 검색어마다 같은 심볼을 다시 나눴습니다. 캐시는 쿼리 안에서만 살아 있으며 다음 질문에서는 새 인덱스를 읽습니다.

이 문서는 **한 Mac의 합성 입력 측정**입니다. 실제 고객 저장소의 정확도·청구액 절감·생산성이나 다른 모델과의 호환성을 입증하지 않습니다.

## 비교 조건

- 2026-10-01, Apple Silicon arm64·8 processors, macOS 27.0 (26A428), Swift 6.4, Release 빌드. 로컬 SwiftPM은 `--build-system native`를 사용했습니다.
- 결정적으로 생성한 Swift 파일 500개, 함수 12,000개, 소스 1,985,720 bytes. 실제 프로젝트·설정·대화 기록을 사용하지 않았습니다.
- 검색어는 `login session token cache validation service`, 본문 예산은 8,000 추정 토큰. Git 신호는 껐습니다.
- 기준본은 최종 보안 코드와 같은 코드에서 **ContextOptimizer.swift만** `b28bb8b34c4e32c3d112324e62370ff9d2449dfc`의 최적화 전 구현으로 교체해 별도 빌드했습니다. 따라서 아래 비교에는 양쪽 모두 최종 파일 경계 보호가 포함됩니다.
- 각 실행은 새로운 합성 프로젝트를 만들었습니다. 프로세스 실행은 전후 각각 3회이며 표는 그 중앙값입니다. 프로세스 안에서 스캔·증분 인덱스는 9회, 순위 계산은 7회, 전체 쿼리는 5회의 중앙값을 냅니다. 초기 인덱스는 실행당 1회입니다.
- CPU 고정·다른 프로세스 중지·순서 무작위화·통계적 유의성 검정은 하지 않았습니다. 파일 시스템 캐시와 실행 순서 영향이 있습니다.

## 최종 보안 코드를 맞춘 결과

| 측정 | 최적화 전 | 최적화 후 |
|---|---:|---:|
| 초기 스캔·파싱·인덱스 | 303.580 ms | 300.244 ms |
| 스캔 | 14.341 ms | 14.364 ms |
| 변경 없는 증분 인덱스 | 18.307 ms | 18.534 ms |
| 순위 계산 | 920.455 ms | 162.522 ms |
| 전체 최적화 쿼리 | 1,360.734 ms | 599.196 ms |
| 최대 RSS | 28.969 MiB | 32.938 MiB |

이 입력에서 순위 계산 시간은 약 **82.3%**, 전체 쿼리 시간은 약 **56.0%** 줄었습니다. 최대 RSS는 약 **4.0 MiB(13.7%) 증가**했습니다. 어휘 재사용에 필요한 메모리 비용이 있으며 스캔·인덱싱 시간을 개선했다는 결과로 해석하지 않습니다. RSS는 macOS `getrusage`의 프로세스 high-water 값이고, 소스 생성·인덱싱·검색까지 포함합니다.

선택된 파일은 모두 7개, 본문은 모두 7,994 추정 토큰이었습니다. 전체 순위의 경로·점수·토큰 수와 생성한 본문을 합친 SHA256은 **6회 모두 동일**했습니다.

```text
3e9c09c35c92b5a62b460bb4b2cfca7236fec8b719704cf98007434369555922
```

이 입력에서 선택 결과를 보존했다는 증거입니다. 다른 프로젝트의 검색 결과나 휴리스틱의 전체 정확도를 증명하지 않습니다. 각 실행의 수치·환경·코드 해시는 [측정 JSON](benchmarks/lexical-500-files.json)에 있습니다. 이전 점검 단계의 보안 강화 전 측정에서는 전체 쿼리 중앙값이 1,352.175→584.833 ms, RSS가 26.141→31.516 MiB였으며, 이후 파일 경계 검사를 추가했기 때문에 위 표를 최종 비교로 사용합니다.

## 파일 감시와 대시보드 데이터

10,000개의 합성 이벤트 경로에서 이전 문자열 필터는 7,000개, 새 필터는 4,000개를 재인덱싱 대상으로 분류했습니다. 새 정책은 인덱스 디렉터리 자체·빌드 디렉터리 자체·민감 파일 등의 잡음을 제외합니다. 분류 시간 중앙값은 이전 66.193 ms, 이후 52.639 ms였습니다. 실제 파일 감시 데몬의 CPU·배터리 절감률이나 디스크 이벤트 처리량을 측정한 결과는 아닙니다. 소스 변경을 실제 FSEvents가 전달하는지는 별도 자동 테스트로 확인합니다.

빈 임시 홈에 만든 JSONL 기록 4개(총 1,176,000 bytes, 880,000 합성 토큰)의 집계는 초기 58.398 ms, 반복 읽기 1.103 ms, 메모리 결과 재사용 약 0.000125 ms였습니다. **UI 렌더링은 측정하지 않았고 이전 버전과의 속도 비교도 아닙니다.** 매우 작은 재사용 시간은 타이머 해상도·호출 비용의 영향을 받습니다. 기존 기록 캐시가 있는 경로의 특성을 보여 주며 실제 사용자 로그 처리 성능을 보장하지 않습니다.

## 재현과 회귀 검사

```sh
swift build -c release
# 존재하지 않는 빈 임시 경로만 사용합니다.
.build/release/contextos-bench /tmp/contextos-bench-unique 500
python3 scripts/benchmark_context.py --binary .build/release/contextos-mcp --verify
swift test
```

기준본을 재현하려면 별도 복사본에서 위 기준 커밋의 `ContextOptimizer.swift`만 교체하고 같은 벤치마크를 Release로 빌드합니다. 기본 벤치마크는 사용자 세션 로그를 읽지 않습니다. `--dashboard`는 미리 만든 빈 `<fixture>/home`을 `CFFIXED_USER_HOME`으로 지정한 경우에만 합성 집계를 허용합니다. 기존 디렉터리를 입력하면 중단합니다.

MCP 회귀 검사는 실제 stdio 바이너리의 6개 도구, 명시적 파일명 검색, 작은 예산의 본문 슬라이싱, 응답 전체 예산, 세션 중복 제거·fresh, 강제 재인덱싱, 민감 파일·중첩 ignore·규칙 링크·인덱스 링크·보호 루트와 잘못된 JSON 진단을 확인합니다. 임시 홈을 쓰고 실제 AI 설정·로그·키·분석 기록과 네트워크를 차단합니다. CI는 두 아키텍처에서 작은 합성 입력의 동작을 검사하며 일정한 성능 수치를 보장하지 않습니다.
